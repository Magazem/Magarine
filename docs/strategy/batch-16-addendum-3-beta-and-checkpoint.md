## 3. Ruling 28 — what stands in for the owner's walk

The owner's walk caught the token wall, the home-directory workspace and the one-at-a-time queue, and the suite caught none of them. The Orchestrator's own walk found the token wall first and missed the other two. A person who knows the product is not a new user. So the substitute is two walks, not one, and neither is the suite:

1. **The lead's cold walk.** From the README only, on a fresh state directory and a fresh project folder, every command typed as written, every deviation from the README recorded as a finding before it is worked around. Same as the batch 15 walk, with the cold start made a condition rather than a habit.
2. **A stranger's walk.** A fresh agent, sonnet, hired for one session with **only the README and a terminal**: no repository, no team history, no addenda, no chat. Its brief is one paragraph: "You are a developer who has just been given this tool. Follow the README to get one small task done. Report every point where you were stuck, confused, or had to guess, in the order you met them, and what you did about it." Its findings are verified by the Orchestrator like any teammate's claim. It is retired after reporting. This is the nearest thing to a new user the team can produce, and its ignorance is the asset; nothing may be explained to it that the README does not say.

Both walks are recorded in the batch's `RESULT.md`, findings ruled before close, per rule 20. The real-run conditions stay as written. The suite's browser tests run on the walk machine and the summary line is quoted, per addendum 2.

**Reading the owner's data ends.** Internal testing uses the team's own state directory. The owner's database is not opened again until the checkpoint, and then only with their walk.
