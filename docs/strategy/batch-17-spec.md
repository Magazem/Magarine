## 0. What this batch delivers, in one sentence

The owner types one command and sees the board in its own window, with the token already inside it, and is told by the operating system when the product needs them. Ruling 27's beta definition, verbatim: *"a daemon and a page the owner does not have to assemble."*

## 1. Ruling 30 — the host starts the daemon itself when none is running, and attaches when one is. It does not supervise.

This is the answer to the question the requirement file put to spec time.

### Evidence, HARD

- `commands/serve.ts` 39-131: `serve()` is a plain async function. It checks for a live daemon, starts the loop, binds, writes `daemon.json`, calls `onListening`, then awaits SIGINT/SIGTERM. Nothing about it is tied to being the top-level command; `cli.ts` 1076-1108 just calls it.
- `commands/token.ts` 1-14 and 68-80: `magarine token` reaches the token by reading `daemon.json` through `checkDaemonFile`, and ruling 20's invariant is stated in the file header: the token never reaches stdout, stderr, a log, **a URL**, a response body, or `--json`. Only the clipboard, and only on stdin.
- `daemonApi.ts` 525-533 and 591-604: `GET /` and `GET /ui/*` are the only unauthenticated routes. Every data route is behind the bearer token.
- `ui/app.js` 247-263 and 1233-1289: the page keeps the token in `sessionStorage` under `magarine.token`, and the only way it gets there today is the input box. 914-916: the stream is a streaming `fetch`, not an `EventSource`, precisely so the token never goes in a URL. 1188-1200: the hash is the view router; an unknown hash falls back to `board`.
- `ui/index.html` 6: `<title>Magarine</title>`, and no favicon link anywhere in the file.
- `ui/browserHarness.ts` 44-64: Chrome is resolved by `MAGARINE_CHROME`, then PATH, then the platform's usual install path, and the strategy is reported. Zero dependencies, spawned with a debugging port.
- This machine (HARD, run this turn): Node 26.2, pnpm 10.33; **no `cargo`, no `dotnet`**; Edge 153 at `C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`; the WebView2 runtime present at `C:\Program Files (x86)\Microsoft\EdgeWebView\Application\153.*`; Chrome at the path the harness already uses. Running `msedge --version` printed `Opening in existing browser session.` — the owner's Edge is running now, so a spawn without its own profile directory would hand our URL to their browser and exit at once.
- `packages/core/package.json`: zero dependencies, `node:sqlite` for the database (`db/index.ts` 1), TypeScript run natively by Node. The README's install is four commands and no build.
- Prior art, HARD: `batch-14-addendum-2-owner-brief.md` line 24 already described the host as one *"which starts the daemon and shows the page"*, line 82 left the shell choice open between Tauri, WebView2 and Electron, and line 114 gave it OS notifications for Needs You and the token handoff. **That document numbers the window host as batch 16**; worker profiles slipped and batch 16 became hardening, so its "16" is this batch, 17 (rule 19: cite it by content, not by number). It is evidence of direction and this ruling agrees with it on every point but the shell, which it left open and section 1 now closes. No Electron, Tauri or WebView2 code exists anywhere in the tree (HARD, `packages/` holds only `core`).

### Why this shape and not the three others

- **A Rust or C# WebView2 shell (Tauri, or a hand-written host).** Neither toolchain is on this machine. Installing one, learning it, and producing a signed-or-not `.exe` is a batch of its own before the first window appears, and it would be paid in session limits while the owner is away. Not now. The WebView2 runtime being present is noted for the late-stage packaging batch; it changes nothing here.
- **Electron.** A second Chromium of roughly a hundred megabytes into a zero-dependency package; its bundled Node does not carry our `node:sqlite`, so the daemon would have to be a child process anyway; native-module rebuilds are the exact build-on-the-owner's-machine step the no-build rule forbids. It buys a custom title bar and a tray icon, neither of which this batch needs.
- **The window attaches only, never starts the daemon.** Cheaper by perhaps forty lines, and it fails the beta sentence: the owner would still assemble two things. `serve()` being a function makes starting it in-process the cheap option, not the expensive one.
- **The window starts AND supervises the daemon (restart on crash, detached lifetime, no console).** That is the late-stage requirement's body, and the owner said explicitly it is not now. More to the point it needs decisions only they can make (does closing the window stop the work? is there a tray icon? what does a crash look like with no terminal?), and they are away.

### The ruling

1. **One new command, `magarine app`.** Same flags as `serve` (`--adapter`, `--max-parallel`, `--port`, `--run-timeout`, `--tick-interval`, the fake-adapter flags, `--state-dir`, `--db`), plus `--browser <path>` as an explicit override. `serve` stays exactly as it is: the windowless route, for scripts, tests and anyone who wants a plain browser tab.
2. **Owned mode.** If no live daemon exists for the state directory, `app` calls `serve()` in its own process, exactly as the `serve` command does, prints the same listening line, then opens the window. The host's lifetime is the daemon's: Ctrl+C stops the daemon (with Role A item 1's line when work was cancelled) and then closes the window. **Closing the window never stops the daemon and never cancels work.** The host prints one line when the window closes and the daemon is still up: `window closed; the daemon is still running (N tasks in flight) -- \`magarine app\` reopens the window, Ctrl+C here stops the daemon`. With nothing in flight the same line without the parenthesis. **OWNER TASTE:** a window whose close does not stop the work. Fallback shipped: this. The alternative (close stops everything) destroys partial spend on a click, and the case for it is a late-stage case, when there is no terminal to say otherwise.
3. **Attach mode.** If a live daemon exists (started by `serve`, or by an earlier `app` in another terminal), `app` opens the window against it and lives until the window closes, then exits with no output. Ctrl+C in attach mode closes the window and prints `window closed; the daemon (pid N) started elsewhere keeps running`. The daemon is never touched from attach mode.
4. **The token handoff is a one-time launch code, not the token.** Ruling 20 forbids the token in a URL, and a Chromium command line is a URL in a process listing. So the host never puts the token anywhere. Instead:
   - `POST /launch-code`, behind the bearer token like every data route: mints a 32-byte random hex code, single use, sixty seconds, kept in the request handler's memory. Response `{ code, expiresAt }`. Cap of, say, sixteen live codes; the oldest is dropped past that.
   - `POST /launch-code/exchange`, **unauthenticated, the third and last exception beside `GET /` and `GET /ui/*`**, body `{ code }`. A live, unused code answers `{ token }` once and is burned before the response is written. Anything else answers 404 with `{ error: 'launch code expired or already used' }` and nothing about whether it ever existed.
   - The host reads the token from `daemon.json` exactly the way `magarine token` does (`checkDaemonFile`, never through `onListening`), mints a code, and opens `http://127.0.0.1:<port>/#launch=<code>`. The fragment never reaches the server in the GET.
   - The page, on load, sees `#launch=`, exchanges it, stores the token in `sessionStorage` exactly as if it had been typed, replaces the fragment with the view it would otherwise show, and proceeds. A failed exchange shows the existing gate with the reason: `this launch link has expired -- run \`magarine app\` again, or \`magarine token\` and paste it here`. Rule 9: the page says so, it does not sit on an empty board.
   - **Ruling 20 is amended, not broken:** the exchange response is the second sanctioned path by which the token reaches the owner's own session, and the only response body that ever carries it. The invariant that it never reaches stdout, stderr, logs, `--json`, or any command-line argument is unchanged and is what the tests prove. The code itself is not the token: by the time a process listing can show it, it has been burned.
5. **The window is Chromium's application mode.** `<browser> --app=<url> --user-data-dir=<stateDir>/window --no-first-run --no-default-browser-check --disable-background-mode --window-size=1400,900`, plus whatever the spike in section 2 finds necessary for a clean first window. Its own profile directory is mandatory (the HARD finding above: without it the URL goes to the owner's running browser and our process exits instantly, and the launch code lands in their browsing history). Chromium persists window bounds in that profile, so the owner's last size and position come back for free.
6. **Browser resolution: Edge, then Chrome, then `MAGARINE_BROWSER` or `--browser` wins over both.** Edge first because it is on every Windows 10 and 11 machine an end user could have; Chrome second because it is what this machine's tests already drive and the engine is the same. The strategy is reported on the terminal the way the harness reports Chrome's. With neither found, `app` still starts the daemon in owned mode and prints the page address with `magarine token`, and says in the same line that no browser was found and where it looked — the product degrades to exactly today's product, out loud. **OWNER TASTE:** the window is an Edge window on this machine (Edge's title bar, an Edge process in Task Manager). Fallback shipped: this, with the page's own favicon and title in the taskbar. If they dislike it, `--browser` reaches Chrome today and a real shell is the late-stage batch.
7. **Needs You reaches the owner as an operating-system notification, from the page.** The page already receives `worker_needs_user_decision` and `worker_needs_review` over the stream (`app.js` 112-119, 166-181). On such an event, when notifications are on, it raises a Web Notification with the ticket's title and the inbox item's one-line message; clicking it focuses the window and switches to the Needs You view. **Notifications are turned on by one click in the Needs You panel head** (`notify me: off / on / blocked by the browser`), because Chromium grants the permission reliably only on a user gesture, and the grant persists in the host's own profile so the click happens once. The state is drawn from `Notification.permission` and the owner's own toggle, never assumed (rule 8). **OWNER TASTE:** opt-in by a click rather than asked on first load. Fallback shipped: the click. The alternative, host-side toasts through PowerShell, shows "Windows PowerShell" as the sender and needs no browser permission; held as the fallback if the owner rejects the prompt.
8. **The seam for the late-stage requirement, stated so it is not foreclosed.** `magarine app` is the one entry point. Late stage replaces "the owner types it in a terminal" with "a shortcut or installer runs it detached", adds a tray icon and crash reporting where the terminal line is today, and puts project creation on the page. None of that changes the command, the daemon, the code exchange, or the page. What this batch must NOT do: put daemon-lifetime decisions into the page, or make the window's existence a condition of the daemon's. Both are kept in the host, in one file, so the supervisor later replaces one file.
9. **Windows first, not Windows only.** The resolver already knows macOS and Linux paths for Chrome; `app` is written through it and refuses nothing by platform. Tested on Windows only; `app --help` says so in one sentence. Linux stays parked behind the beta, `linux-leg-design.md` unchanged.

## 2. Item zero: the window spike, before anything else is built on it

The whole batch rests on four facts about Chromium application mode on this machine that I have not observed. Role A proves them first, in under a session, and records the result in `docs/evidence/batch-17-walk/window-spike.md`:

1. `msedge.exe --app=<url> --user-data-dir=<temp>` with the flags in ruling 30 item 5 opens a window with no address bar, no tabs, and no first-run or sign-in interruption. If Edge shows first-run UI, find the flag that suppresses it; if none exists, Chrome moves to first place and the finding says so.
2. The process the host spawned is the browser process, and it exits within five seconds of the window being closed gracefully. Close it the way a person does: PowerShell `(Get-Process -Id <pid>).CloseMainWindow()`, not `Stop-Process`. If Edge keeps the process alive after the window closes, try Chrome; if both do, stop and escalate — the lifecycle in ruling 30 items 2-3 depends on this and the fallback is polling the window list, which I would rather rule on than have built quietly.
3. The page's title and favicon appear in the taskbar entry, not the browser's. Needs Role B's favicon (item 1) to exist first; the spike can use any SVG placeholder and say so.
4. A Web Notification raised from the page in that window appears as a Windows notification, and clicking it focuses the window.

Evidence for each: a screen capture taken by PowerShell (`System.Drawing`, `CopyFromScreen`) saved under the evidence folder and read back, since the owner is away and cannot look. The window is opened on the owner's desktop and must be closed by the spike before it ends, and the temp profile deleted; nothing of the owner's is touched (their Edge stays as it is because of the separate profile directory).

Stop rule: if facts 1 or 2 fail on both browsers, the batch pauses on my desk with the capture, and nothing past Role A item 1 is built.
